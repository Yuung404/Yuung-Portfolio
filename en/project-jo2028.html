CONTEXT & GOALS

Final-year project presented at the E6 exam of the BTS SIO (software development track). The organising committee of the Los Angeles 2028 Olympic Games needs a website: a public part showing the sports, the event schedule and the results, and an admin back-office to manage all of this data.

The project started from a provided codebase that was deliberately imperfect. I approached it like an engineer taking over legacy code: audit, fix, secure, then build the missing features, test them and ship them to production. All in plain PHP, with no framework, to master every mechanism.

APPROACH & PROJECT MANAGEMENT

The project is split into 8 missions tracked on a Trello Kanban board (To do, In progress, Done). Every card has a due date and a checklist; mission 6 is split into one card per managed table, all built on the same checklist (list, create, update, delete, session guard, output escaping, test, commit).

WHAT I BUILT

1. Audit and fix of the provided code
Before building anything, I audited the starter code and found 7 defects. Two broke the site: the FILTER_SANITIZE_STRING filter, deprecated since PHP 8.1, blocked the redirect after login; lowercase table names would have crashed on a case-sensitive Linux server. The others were security flaws: deletion through a plain link with no CSRF protection, SQL errors shown to visitors, double escaping. All fixed in a dedicated commit.

2. Relational database
8 tables in utf8mb4 with the InnoDB engine: sports, venues, countries, genders, events, athletes, administrators, and the PARTICIPER association table with a composite primary key (one result per athlete per event). I wrote a migration adding the nom_epreuve column missing from the provided script, and 7 UNIQUE constraints that block duplicates at database level, on top of the PHP checks (defence in depth).

3. Shared core and security
Every page goes through a single bootstrap file that loads the configuration (kept out of Git), starts a session with hardened cookies (HttpOnly, SameSite=Strict, Secure over HTTPS) and opens a PDO connection using real server-side prepared statements. A function library centralises HTML escaping, the anti-CSRF token, the access guard and input validation.

4. Authentication
Passwords hashed with Bcrypt (password_hash / password_verify), new session ID at login against session fixation, identical response time whether or not the login exists, generic error message, automatic logout after 30 minutes of inactivity, and token-protected POST logout.

5. Back-office: 8 CRUD modules
Administrators, sports, venues, countries, genders, event schedule, athletes and results. Every module follows the same pattern: access guard, token check, server-side validation, duplicate check, integrity check before deletion (a sport used by an event cannot be deleted), prepared statement, confirmation message and redirect (Post-Redirect-Get). Every ID picked from a drop-down list is checked again against the database.

6. Responsive public site
Home, sports, schedule and results pages, built with multi-table SQL joins, with French date formats and a layout adapted to desktop, tablet and mobile.

7. Automated tests
PHPUnit 11 installed with Composer: 15 unit tests on the validation and security functions, and 14 functional tests driving the real site (PHP built-in server + cURL-based simulated browser) against a test database rebuilt before every test. Each test checks the displayed message and the actual database state, including XSS and CSRF attacks.

8. Production release
Public GitHub repository with no secrets (.gitignore + configuration template), an .htaccess file that blocks SQL scripts and internal folders and adds security headers, a re-importable production SQL script that enforces InnoDB, and a PowerShell script that generates the production configuration and uploads the site over FTPS.

SECURITY AT A GLANCE

▸ SQL injection — PDO prepared statements, emulation disabled
▸ XSS — htmlspecialchars on every displayed value
▸ CSRF — 64-character random token, constant-time comparison, POST-only deletions
▸ Passwords — salted Bcrypt, 8 characters minimum, 72 bytes maximum
▸ Sessions — regenerated at login, hardened cookies, 30-minute timeout
▸ Errors — generic message in production, details in the server log
▸ Server — .htaccess: no directory listing, sensitive files 403, internal folders 404
