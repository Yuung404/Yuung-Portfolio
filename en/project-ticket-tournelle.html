CONTEXT & PROBLEM

At the school, technical incidents are reported through Excel, text messages, WhatsApp voice notes or phone calls. The result: lost requests, delays, no figures for management and overloaded IT staff. Ticket'Tournelle is a web portal where every staff member reports an incident and follows its resolution, technicians handle tickets, and management reads indicators.

The client sets 9 constraints, including a named account per person, a French and English interface, an in-house server that we install and run ourselves, and admin accounts managed according to ANSSI guidelines.

WHAT I BUILT

1. Specification and mock-ups
Needs analysis, specification, user stories, ticket lifecycle (open, assigned, on hold, resolved, closed), categories and priorities, then 12 screen mock-ups for the three roles: user, technician and administrator.

2. Database
Conceptual and logical models, then 16 MariaDB tables with constraints and indexes, and 5 SQL views for the dashboard. Several tables are justified by the specification (rooms, allowed status transitions so that any other change is rejected, one-time password reset, security log), and two more were added by migration during development without data loss. Bilingual labels, Argon2id hashes, accounts disabled rather than deleted, least-privilege application SQL account.

3. In-house web server
Debian 13 VM with no desktop, root disabled in favour of a named sudo account. The whole setup is automated in a re-runnable provision.sh: Apache and PHP 8.4, MariaDB listening locally only, HTTPS with TLS 1.2 / 1.3, security headers, UFW firewall (22, 80, 443), Fail2ban, key-based SSH, automatic security updates, nightly database backup. Three test scripts check the database (24 checks), the server (48) and an actual backup restore (9). A release is deployed from the PC with a single command.

4. Application
Framework-free PHP 8.4 with a single router that checks, for every page, the method, the CSRF token, the session and the role's permission. Incident reporting with a verified photo, technician queue sorted by priority, 6-status lifecycle, internal notes, notifications and e-mails in each user's language, server-side SVG dashboard, account administration through activation links.

5. Justified, proven security
For each measure: the threat, the reference (OWASP Top 10, ANSSI, CNIL) and the test that proves it. Prepared statements (sqlmap finds nothing injectable), output escaping and a strict CSP, CSRF tokens, atomic lockout after 5 failures (even with 12 attempts sent at the same instant), other users' tickets answer 404, photos checked by their content.

6. Tests and triple verification
A test runner written for the project: 285 unit and functional tests, 130 checks in a real browser (Playwright, French, English and mobile), 30 on login, 81 on the server. Three cross-checks (two environments, an independent review, a fresh environment) found 23 defects, all fixed with a regression test.

7. Documentation and hand-over
Staff guide with screenshots, technical documentation, security file, acceptance test book, defect and client-exchange logs, professional situation sheet and project report, all gathered in the shared workspace. Hand-over to the client on 4 December 2026.
